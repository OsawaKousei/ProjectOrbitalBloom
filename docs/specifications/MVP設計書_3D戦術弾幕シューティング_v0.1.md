# 3D戦術弾幕シューティング MVP設計書

**Version:** 0.1  
**Date:** 2026-09-26  
**Target Platform:** PC  
**Host Engine:** Unreal Engine 5.x  
**Simulation:** Unreal Engine非依存のC++ GameCore

---

## 1. 文書の目的

本書は「3D戦術弾幕シューティング ゲーム企画書」に記載された構想のうち、最初のMVP（Minimum Viable Product）で実装・検証する範囲を定義する。

本MVPは製品版の縮小版（Vertical Slice）ではない。目的は、以下のコア体験がゲームとして成立するかを最小限の実装で判定することである。

1. 3D弾幕を停止して観察する行為そのものに発見と美しさがあるか。
2. アンカー変更が単なる移動操作ではなく、座標系・位置を選ぶ戦術判断になるか。
3. TACTICAL MODEで考えた後にACTION MODEへ戻る瞬間と、その数秒間の飛行が気持ちよいか。
4. 停止時間を除去したリプレイが、プレイ結果を「3Dの飛行作品」として鑑賞できる品質を持つか。

MVPでは「完成したゲーム」を作るのではなく、上記4点についてGo / Iterate / No-Goを判断できる状態を完成とする。

---

## 2. MVPの一文要約

**美術性を持つ3種類の立体弾幕を、時間停止中に観察し、Follow / Convergeアンカーで移動座標系と位置を選び、短いACTION MODEで回避し、その結果を停止時間なしの自動リプレイで鑑賞する1ボス戦プロトタイプ。**

---

## 3. 検証仮説

### H1. 立体弾幕の観察が遊びになる

正面視点では把握しにくい弾幕をTACTICAL MODEで別角度から見ることで、「空洞」「通路」「薄い方向」「構造の規則性」を発見できること。

プレイヤーの感想として、単に「安全な場所を探した」ではなく「横から見たら構造が分かった」「この弾幕はこういう形だった」と説明できる状態を目標とする。

### H2. アンカー選択が戦術になる

Follow状態のまま避け続けるだけでなく、「現在の座標系では不利なので別位置へ移る」「この方向から弾幕へ入る」といった判断が自然に発生すること。

### H3. 計画後のACTION MODEが爽快である

TACTICAL MODEで考えた後、数秒間のACTION MODEで弾幕を読み切って抜ける際に、緊張から解放への明確な感情変化が生まれること。

ポーズ頻度の少なさ自体は評価対象としない。頻繁に停止してもよい。そのうえで、再開した瞬間に「実行する快感」が存在するかを検証する。

### H4. プレイ結果を見返す価値がある

TACTICAL MODEでの思考時間を圧縮または除外し、ゲーム内で時間が進行した区間のみをつないだリプレイが、単独で鑑賞可能な映像になること。

「今の軌道をもう一度見たい」という自発的な反応が起きることを重要な成功兆候とする。

## 4. MVPスコープ概要

| 項目 | MVP仕様 |
|---|---|
| プレイ形式 | ボス戦1つのみ |
| ゲーム内進行時間 | 約60〜90秒を目安。TACTICAL MODE中の実時間は含めない |
| ボス | 1体。基本静止または低速移動・低速回転 |
| 弾幕 | 3パターン |
| プレイヤー操作 | ACTION中は2軸移動のみ |
| モード | ACTION MODE / TACTICAL MODE |
| アンカー | Follow、Converge。Converge到達後は内部的にFixed |
| 射撃 | なし |
| ボスHP | なし |
| 被弾 | 記録・フィードバックのみ。原則としてプレイを中断しない |
| 危険表示 | 短時間先に自機へ接近する弾のみ簡易強調。ON/OFF可能 |
| リプレイ | 思考時間除去、自機軌跡、自動カメラ2〜3種 |
| 美術 | 暗い背景＋発光弾＋残像を中心とした最低限の完成VFX |
| 入力 | Keyboard / MouseをMVP基準。Gamepadは後回し |

## 5. プレイヤー体験フロー

1. 起動すると直接ボス戦へ入る。
2. 短い操作ガイドを表示する。
3. Follow状態で第1弾幕が開始する。
4. プレイヤーは任意のタイミングでTACTICAL MODEへ移行する。
5. 時間が停止し、カメラを回して弾幕の立体構造を観察する。
6. 必要ならConvergeアンカーを3D空間に配置する。
7. ACTION MODEへ戻り、アンカー方向への奥行き移動と2軸回避を同時に行う。
8. アンカー到達後はFixed状態へ遷移する。
9. 必要に応じてボスFollowへ戻る。
10. 3種類の弾幕を通過すると戦闘終了。
11. 自動的にリプレイを再生する。
12. Replay / Restart / Exitのみ選択可能とする。

タイトル画面、ステージ選択、セーブデータ、ストーリー画面などはMVPでは作らない。

---

## 6. ACTION MODE設計

### 6.1 操作

ACTION MODEでプレイヤーが行う操作は原則として2軸移動のみとする。

- W / S: 現在の移動平面における上下
- A / D: 現在の移動平面における左右
- Tacticalキー: TACTICAL MODEへ移行

前後方向を直接操作するキーは設けない。奥行き方向の挙動は現在のアンカー状態によって決定する。

### 6.2 移動

- 移動速度は固定値から開始する。
- 加減速は最小限とし、操作感確認後に調整する。
- 移動平面は現在の座標系から導出する。
- アンカー切替時の平面・姿勢変化には短い補間を入れ、入力方向の急変を抑える。

### 6.3 被弾

MVPでは一撃死・残機・HP制を採用しない。

被弾時は以下のみ行う。

- ヒットVFX / SE
- 被弾回数を記録
- リプレイ上のイベントとして記録
- 短い無敵時間を入れ、同一弾幕で連続判定されないようにする

プレイテストの目的は攻略難易度ではなく、観察・移動・飛行体験の評価であるため、被弾によって試行を頻繁に中断しない。

---

## 7. TACTICAL MODE設計

### 7.1 基本仕様

- ゲームシミュレーションを完全停止する。
- 停止回数・停止時間にペナルティを設けない。
- ACTION復帰直後の強制コミット時間はMVPでは設けない。
- ポーズ連打が可能であることを受け入れたうえで、飛行・弾幕・リプレイの美しさが提供価値として成立するかを検証する。

### 7.2 カメラ

最初から完全なnoclip自由カメラにはしない。

MVPでは以下を実装する。

1. Player Orbit: 自機中心の回転・ズーム
2. Boss Orbit: ボス中心の回転・ズーム
3. 必要最小限のパン

完全自由移動カメラは、Orbit方式だけでは立体構造を十分に観察できないことが確認された場合に追加する。

### 7.3 表示

TACTICAL MODE中のみ以下を表示する。

- 自機位置
- 現在の移動平面（半透明ディスクまたはグリッド）
- ボス位置
- 現在のAnchor状態
- Convergeアンカー候補位置
- 自機とアンカーの距離
- 危険弾ハイライト

安全経路や「正解ルート」は表示しない。

---

## 8. アンカー仕様

### 8.1 Follow Anchor

MVP開始時の標準状態。

- 対象はボス1体のみ。
- ボスとの距離を原則維持する。
- プレイヤーの2軸入力はボスを中心とした接線方向の移動へ変換する。
- ボス周囲を回り込む立体移動が2軸入力で成立することを確認する。

### 8.2 Converge Anchor

TACTICAL MODE中に任意の3D位置を指定する。

- 自機は指定点へ向かう奥行き速度を持つ。
- 移動中も2軸回避が可能。
- 到達後はFixed状態へ遷移する。
- Converge速度は固定パラメータとして開始し、プレイテストで調整する。

### 8.3 Fixed State

MVPでは独立した「Fixed Anchorを設置する操作」は用意しない。

Converge到達後のみFixed状態となる。

- 奥行き速度0
- 到達時に保存した移動平面内のみ2軸移動
- Followへ戻る操作を用意する

### 8.4 3Dアンカー配置UI

MVPでは以下の方式を基準案とする。

1. TACTICALカメラ中心からレイを伸ばす。
2. 画面上の2D位置で方向を指定する。
3. マウスホイール等でレイ上の深度を調整する。
4. 3D空間にGhost Anchorを表示する。
5. 距離と移動後の平面を可視化する。
6. Confirmで確定する。

このUIが煩雑な場合は、ボス中心の仮想球面上へ配置する簡略方式も比較テストする。

## 9. 弾幕コンテンツ

MVPでは3種類のみ作る。各弾幕は「難易度の違い」ではなく「必要な空間認識の違い」を持たせる。

### Pattern A: Spherical Shell / Flower

**目的:** 「視点を変えると構造が分かる」を最も分かりやすく検証する。

- ボス中心から球殻状に弾を放出
- 球面上に1〜3個の明確な空洞または薄い領域を設ける
- 正面からは空洞位置が把握しにくい
- 横・斜めから見ると構造が明確になる
- 空洞へConvergeして抜けることができる

### Pattern B: Rotating Helix / Ring Tunnel

**目的:** 静的な安全地帯ではなく、時間変化する立体構造を読む体験を検証する。

- 複数のリングまたは螺旋帯が回転しながら進行
- 特定角度・タイミングで通路が形成される
- Followで回り込む判断とConvergeの両方が利用可能
- 弾幕を横から見たときに美しい立体構造が明確に分かることを重視

### Pattern C: Planar Wall / Lattice

**目的:** 現在の移動平面を変更する必要性を検証する。

- 平面状または格子状の弾幕が空間を横断
- 現在のFollow面では安全域へ到達しにくい配置にする
- 別角度・別位置へConvergeすることで抜けやすくなる
- 「弾を避ける」より「戦う平面を変える」判断を誘発する

---

## 10. ボス仕様

MVPのボスはゲーム内容ではなく弾幕発生源として扱う。

- ボス1体
- 複雑なAIなし
- 基本位置を維持
- 必要に応じて低速移動・低速回転のみ
- Pattern A → B → Cを順番に実行
- HPなし
- 攻撃可能部位なし
- 破壊演出なし

外見はシルエットと発光部位が判別できる最低限のモデルでよい。

---

## 11. 危険弾表示

MVPでは高度な経路予測を実装しない。

各弾について短時間先の最接近距離を近似し、一定条件を満たす弾のみTACTICAL MODEで軽く強調する。

入力候補:

- 自機位置
- 自機現在速度
- 弾位置
- 弾速度
- 予測時間窓

表示は「注目対象」を示すだけとし、回避方向や安全経路は提示しない。

危険表示の有無による体験差を確認できるよう、開発用設定で即時ON/OFF可能にする。

---

## 12. 美術・VFXの最低品質

本MVPでは美術性自体が検証仮説に含まれるため、完全なDebug表示のみでは評価しない。

一方で、専用モデルや大量のアセット制作は行わない。

### 必須

- 暗く情報量の少ない背景
- 発光する弾
- 弾種・構造を識別できる色または形状差
- 移動方向を理解できる残像またはTrail
- 自機の軌跡が読み取れるVisual
- Bloom等の基本Post Process
- TACTICAL移行時の視覚的変化
- ACTION復帰時の明確な演出的アクセント

### 方針

「高品質な素材」ではなく「完成した美術意図」を示す。

弾幕は障害物ではなく、時間停止中に鑑賞できる空間造形としてデザインする。

---

## 13. Audioの最低仕様

- BGM 1曲または1ループ
- ACTION / TACTICALで音響状態を変化させる
- TACTICAL時はローパス、減衰、残響等で時間停止感を出す
- ACTION復帰時に音響的な解放感を付与する
- 被弾SE
- アンカー確定SE
- Converge到達SE

音響も「思考 → 実行」の落差を作る要素として扱う。

---

## 14. リプレイMVP

リプレイは本MVPの必須機能とする。

### 14.1 記録対象

- GameCore内のゲーム時間
- 自機位置・姿勢
- Boss状態
- Bullet状態または再生に必要なPattern状態
- Anchor変更イベント
- TACTICAL開始・終了イベント
- 被弾イベント

MVPではディスク保存を必須としない。1プレイ分をメモリ上に保持できればよい。

### 14.2 再生

- TACTICAL MODE中の実時間は再生しない
- GameCoreの進行時間のみ連続再生する
- 通常速度と0.5x程度のスロー再生を開発用に用意

### 14.3 自動カメラ

最低2種類、目標3種類。

1. Chase: 自機追従
2. Wide / Boss Orbit: ボスと弾幕全体を見せる
3. Side / Cinematic: 自機軌跡と弾幕形状が同時に見える固定・半固定視点

MVPではカメラエディタを作らない。

### 14.4 軌跡表示

自機の移動軌跡を線または残光として表示できるようにする。

通常リプレイではOFFでもよいが、評価用にON/OFF可能とする。

### TACTICAL MODE

## 16. 技術アーキテクチャ

### 16.1 基本原則

ゲーム状態の正本（Source of Truth）はUnreal Engine側に置かない。

Unreal EngineはHostとして以下を担当する。

- Rendering
- Camera
- Input
- UI
- Audio
- VFX / Niagara
- Asset Loading
- Editor / Debug Tool

ゲームルールは独立した純C++ GameCoreが担当する。

### 16.2 GameCore

GameCoreはUnreal Engineの型・APIへ依存しない。

禁止例:

- FVector / FQuat / FTransform
- UObject / AActor / UActorComponent
- UWorld
- TArray / TMap
- Niagara / Chaos API

GameCore内部で独自のVec3、Quat、EntityId、配列型等を使用する。

### 16.3 GameCore責務

- Fixed-step simulation
- Player state
- Boss state
- Anchor state
- Coordinate frame
- Bullet state
- Bullet pattern generation
- Collision
- Danger estimation
- Mode / game time
- Replay state / event recording

### 16.4 Unreal Host責務

- Keyboard / Mouse入力をGameCore Inputへ変換
- GameCoreのRenderSnapshotを取得
- 自機・ボスのMesh描画
- 大量弾の描画
- NiagaraによるGlow / Trail / Hit等の演出
- Tactical visualization
- Camera
- UI
- Audio
- Replay camera

### 16.5 シミュレーション更新

GameCoreは固定時間刻みで更新する。

初期設定は120 Hzを候補とするが、60 / 120 Hzを容易に比較できるようにする。

Rendering frame rateとSimulation tickを分離する。

### 16.6 弾の表現

弾1発ごとにAActorを生成しない。

GameCoreでは連続配列またはデータ指向構造で保持する。

Unreal側はRenderSnapshotをまとめて受け取り、Instanced Static MeshまたはNiagara等で描画する。

ゲームルール上の弾位置・衝突判定をNiagaraのParticle状態へ依存させない。

## 17. コンテンツデータ

MVP段階では弾幕専用GUIエディタを作らない。

PatternはC++定義またはエンジン非依存の簡単なデータ形式から読み込む。

将来のエンジン移行を考慮し、Unreal固有のDataAssetを唯一の原本にはしない。

データ例:

```yaml
pattern: spherical_shell
radius: 40
expansion_speed: 12
hole_count: 2
hole_angle_deg: 18
```

MVPを通じて必要なパラメータ体系を把握した後、専用Bullet Pattern Editorの要件を定義する。

## 18. パフォーマンス検証

MVPでは製品版の対象ハードウェアを決定しない。

ただし設計妥当性確認として以下を計測する。

- Typical: 同時弾数 1,000〜2,000程度
- Stress: 同時弾数 5,000程度
- GameCore simulation time
- Unreal rendering time
- Tactical visualization追加時の負荷
- Replay時の負荷

弾数自体を目標値にはしない。必要な美術表現を維持した状態で、シミュレーションと描画が分離できていることを確認する。

## 19. プレイテストと評価

### 19.1 観察項目

#### TACTICAL

良い兆候:
- 指示されなくても視点を変えて弾幕を見る
- 弾幕構造について言語化する
- 同じ弾幕を別角度から見たがる

危険な兆候:
- カメラ操作を単なる作業と感じる
- 正面だけ見て再開する
- 弾幕の立体構造が理解できない

#### Anchor

良い兆候:
- 「ここへ移れば抜けられる」と意図を持って配置する
- FollowとConvergeを状況で使い分ける

危険な兆候:
- 適当にAnchorを置く
- Anchorを使わず2軸回避だけで十分になる
- 3D配置操作が思考より負担になる

#### ACTION

良い兆候:
- 再開前に緊張が生まれ、突破時に解放感がある
- 数秒間継続して飛行したくなる
- 「読み切った」感覚を口にする

危険な兆候:
- ACTION開始直後に機械的に再停止するだけになる
- 実行部分が観察の確認作業にしか感じられない

#### Replay

良い兆候:
- 自発的に最後まで見る
- 別カメラで見たがる
- 自分の軌跡について話す
- もう一度プレイして違う軌道を作ろうとする

危険な兆候:
- 即座にSkipする
- ゲームプレイと関係ない映像だと感じる
- 自分の選択が軌跡に反映されていると感じない

### 19.2 収集する定量データ

- 実プレイ時間
- GameCore進行時間
- TACTICAL総時間
- TACTICAL回数
- 1回あたり停止時間
- Anchor配置回数
- Follow復帰回数
- 被弾回数
- 弾幕ごとの通過時間
- 自機総移動距離
- Replay再生時間 / Skipタイミング

これらはプレイヤーを採点するためではなく、体験を理解するために使用する。

## 20. Go / Iterate / No-Go判定

### Goの兆候

- 多くのテスターが3D弾幕の構造を「発見」として捉える
- Anchor位置に明確な意図が見られる
- ACTION復帰に緊張と爽快感がある
- Replayを自発的に鑑賞する
- 「別ルートで飛んでみたい」という再試行動機が生まれる

### Iterate

- コンセプトへの反応は良いが、カメラまたはAnchor UIが操作負荷になっている
- ACTIONは気持ちよいが弾幕構造が分かりにくい
- Replayは魅力的だがプレイ中の観察が弱い

この場合はコア仮説を捨てず、UI・カメラ・弾幕デザインを変更する。

### No-Goまたは大幅再設計の兆候

- 視点を変えても弾幕の理解や発見につながらない
- Anchorが戦術ではなく煩雑な移動操作にしかならない
- ACTIONが「答え合わせ」にしか感じられない
- 美術を整えてもReplayを見る動機が生まれない

---

## 21. 明示的にMVP外とするもの

以下は実装しない。

- 道中ステージ
- 直進アンカー
- プレイヤー操作による独立Fixed Anchor設置

## 23. MVP完成条件

以下をすべて満たした時点を「MVP完成」とする。

1. Unreal Engine上で1ボス戦が開始から終了までクラッシュなく実行できる。
2. GameCoreがUnreal Engine非依存で単体ビルド・テスト可能である。
3. ACTION MODEでは2軸移動のみで操作できる。
4. TACTICAL MODEで時間停止・弾幕観察・Anchor配置ができる。
5. Follow → Converge → Fixed → Followの遷移が成立する。
6. 3種類の立体弾幕が、それぞれ異なる空間判断を要求する。
7. 弾幕が最低限の美術品質で表示される。
8. 被弾が検出・記録される。
9. 危険弾表示をON/OFFできる。
10. プレイ終了後、停止時間を除去した自動リプレイを再生できる。
11. 自機軌跡と最低2種類のReplay Cameraを確認できる。
12. プレイテスト用の基本ログが取得できる。
13. H1〜H4を第三者テスターで評価できる。

## 25. 設計上の原則

MVP開発中は以下を優先する。

**1. 面白さの仮説を技術完成度より先に検証する。**  
自作レンダラー、汎用エディタ、製品版UI等は作らない。

**2. ただしGameCoreとUnrealの境界だけは最初から守る。**  
将来エンジンを変更できる出口を維持する。

**3. ポーズ頻度をシステムで矯正しない。**  
頻繁な停止を許容し、その結果として生まれる飛行・弾幕・リプレイの美しさに価値が成立するかを検証する。

**4. 美術性はMVPの評価項目であり、後工程ではない。**  
弾幕が立体造形として美しく見える最低限のVFXを必須とする。

**5. コンテンツ量でごまかさない。**  
1ボス・3弾幕で成立しない場合、敵や装備を増やしてもMVP成功とはみなさない。
